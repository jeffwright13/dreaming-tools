# Dreaming Tools Decisions

## 2026-10-13: Use the public catalog without account authentication

The extension reads `https://app.dreaming.com/videos/prod/es.json`, which contains video IDs, series IDs, and raw difficulty scores. Account credentials and session data are unnecessary for enhancing cards already rendered by Dreaming.

## 2026-10-13: Reproduce Dreaming's score conversion

Dreaming's client converts raw ratings from the range 200–2600 to a rounded 0–100 value. Reproducing that calculation keeps extension badges consistent with native badges.

## 2026-10-13: Show series ranges

A series has no individual difficulty score. The extension displays the minimum and maximum rounded episode difficulties, or one value when all scored episodes round identically.

## 2026-10-13: Use a framework-free Manifest V3 content script

The feature requires only catalog indexing, DOM matching, badge insertion, and mutation observation. Plain JavaScript avoids a build step and keeps local installation transparent.

## 2026-10-13: Own extension badge styling

Stable data attributes and semantic Dreaming class names identify cards, while extension-specific classes style inserted badges. Generated CSS-module class names are intentionally avoided because they can change between deployments.

## 2026-10-13: Offer behavior and appearance presets

A synchronized options page offers Enhanced everywhere, Fill missing difficulties only, and Original Dreaming behavior. Appearance uses tested style, size, and position presets instead of arbitrary CSS controls to preserve readability and contrast.

## 2026-10-13: Select catalogs from language routes

The product is Dreaming rather than a Spanish-only service. The extension maps `/spanish/` to `es.json` and `/french/` to `fr.json`, uses language-neutral terminology, and keeps the route-to-catalog mapping easy to extend.

## 2026-10-13: Support desktop Chromium browsers first

The initial support policy covers the current and previous stable Chrome versions across macOS, Windows, and Linux, plus current Edge on Windows. Shared Chromium internals reduce implementation risk, but release claims still require a manual browser/platform matrix. Firefox and mobile support remain separate future features.

## 2026-10-13: Use layered compatibility testing

Vitest and jsdom remain the fast gate for logic and DOM behavior. Planned fixture-based browser tests will load the real extension without Dreaming credentials, while authenticated live-site smoke tests remain a manual release gate. CI must never store Dreaming credentials, cookies, or browser profiles.

## 2026-10-13: Keep permissions and data flow minimal

The extension stores only validated display preferences, fetches public catalogs with credentials omitted, and has no developer server or analytics. Chrome synchronized storage may pass preferences through the user's Google account, but the developer does not receive them. Any future permission, network destination, storage field, telemetry, or authentication change requires renewed security review and updated privacy disclosure.

## 2026-10-13: Use neutral original branding for beta icons

The icon combines a play symbol with ascending difficulty bars in the extension's charcoal and green palette. It does not copy Dreaming's logo or imply endorsement, reducing branding risk before outreach to Dreaming Languages.

## 2026-10-13: Package from an exact runtime allowlist

A dependency-free Node script creates a deterministic ZIP from the manifest, four PNG icons, and six runtime source files. It rejects version mismatches, missing manifest references, and unexpected archive contents. Development files, credentials, documentation, tests, and dependencies cannot enter the package through directory-wide copying.

## 2026-10-13: Protect main with mechanical gates

Changes to `main` require an up-to-date pull request, the `Test and audit` status check, linear history, and resolved conversations. Force pushes and branch deletion are blocked, and administrators are subject to the rule. No approving review is required while the project has a single maintainer, avoiding a self-review deadlock while retaining CI and pull-request history.

## 2026-10-13: Default to preserving Dreaming's presentation

Fresh installations preserve Dreaming's native badges and add small, upper-right badges in Dreaming style only where difficulty is missing, matching Dreaming's native placement. Enhanced-everywhere behavior and styling remain available as explicit options. Lower-right placement is excluded because Dreaming reserves that corner for video duration. This least-intervention default reduces visual disruption while retaining safe configurability; valid supported settings already stored by a user remain unchanged after an update.

## 2026-10-19: Show watch-page difficulty as metadata chips

Watch pages show video difficulty, plus the series range when applicable, as chips at the start of Dreaming's metadata badge row instead of overlaying the player. An overlay would compete with player controls and changing frames, disappear in fullscreen unless injected into the player, and cannot enter the cross-origin YouTube embed. The row has stable `data-testid` hooks shared by both player variants. The extension does not detect or defer to other extensions that add similar chips, because coupling to third-party markup is fragile; users running both may see duplicate information.

## 2026-11-05: Grow into Dreaming Tools as one extension with feature switches

The repository will host more than the difficulty badges, starting with a subtitle de-emphasis tool for listen-only practice. The extension is renamed Dreaming Tools and stays a single extension, with an independent enable switch per feature, rather than becoming several extensions or repositories. All planned tools run on the same Dreaming pages with the same host permission, so separate extensions would add installs, release processes, and duplicated packaging without reducing permissions. The extension was unpublished at the time of the rename, so no store listing or users' installs are broken. Synchronized storage keys are unchanged, so beta testers keep their settings.

## 2026-11-05: Replace Original Dreaming mode with an enable switch

The difficulty feature's Original Dreaming behavior was already an off switch. Keeping it next to a per-feature enable switch would offer two controls for the same state, so it was removed. A stored `behavior: "original"` migrates to `difficultyEnabled: false` during normalization; an explicitly stored switch takes precedence. Settings are read by key list rather than with defaults, because Chrome fills defaults into the result and would otherwise hide the legacy value. A disabled difficulty feature no longer downloads the catalog, which also slightly reduces network use compared with the old Original mode.

## 2026-11-05: Isolate features behind a single update contract

Each feature exposes only `update(settings)` and receives the whole normalized settings object, and `content.js` calls every feature independently, logging rather than propagating a feature's error. This keeps features unaware of one another, lets any combination be enabled at once, and lets a broken feature fail without disabling the rest. Content scripts remain classic scripts sharing `globalThis` namespaces because Manifest V3 content scripts do not support ES module imports.

## 2026-11-05: Style subtitles through root classes, never the player

The subtitles feature sets classes on `<html>` and a static stylesheet targets Shaka Player's `.shaka-text-container`, instead of editing the player or observing subtitle mutations. The container exists only while the player's own Subtitles setting is on, so the player's choice remains the single source of truth and the extension never turns subtitles on. Styling through CSS survives the player re-creating the container, works in fullscreen, and needs no page observer. The class comes from the Shaka library rather than Dreaming's generated CSS-module names, consistent with the brief.

## 2026-11-05: Make subtitle de-emphasis opt-in with blur as the default

Subtitles default to off so the update changes nothing until a learner chooses it. Blur is the default style because it is unreadable at a glance yet still shows that a line is present; Small and faint keeps the learner's existing habit of tiny on-screen text, and Hidden removes even the blurred bar. All three are presets, matching the earlier decision to offer tested presets rather than arbitrary CSS.

## 2026-11-05: Reveal with a configurable physical key, hold or toggle

Learners differ, so reveal is configurable: Hold (default, because releasing the key always restores the listen-only state) or Toggle with auto-hide (default 5 seconds, so a toggle cannot be forgotten). The key is stored as `KeyboardEvent.code` so it is layout independent and limited to letter, digit, and punctuation keys; `S` was verified on a live watch page to trigger no player shortcut. Key handling runs in the capture phase and consumes the key only while subtitles are shown and the user is not typing, so other pages and the comment box behave normally. Losing window focus re-hides because the key release may never arrive. Replaying the previous line was considered and deferred to keep the first version small.

## 2026-11-05: Read options controls directly instead of FormData

Saving through `FormData` reset a switched-off feature's settings, because `FormData` omits controls inside a disabled fieldset; the difficulty options had this bug since the enable switch was added. The options page now reads every setting from its control, which also handles checkbox and numeric values explicitly.

## 2026-11-05: Extend subtitles into YouTube embeds with a guarded content script

Dreaming now serves many videos through a cross-origin YouTube embed, whose captions the Dreaming page cannot style or observe. A second content script runs in `https://www.youtube.com/embed/*` frames and acts only when its immediate and only ancestor is `https://app.dreaming.com`; the manifest cannot express that restriction, so the check runs first and exits otherwise. This adds www.youtube.com to Chrome's install warning, which was accepted because otherwise the feature would not work on most current videos; the privacy policy discloses the access. Reveal keys pressed on the Dreaming page are forwarded to the frame by `postMessage` with an exact target origin, and the frame accepts only Dreaming-origin messages of a fixed shape, so other pages cannot drive it. Drawing replacement captions from YouTube caption data was rejected as far more complex and as requiring the extension to handle subtitle text. YouTube's caption class names are not a public interface, a documented maintenance risk.

## 2026-11-06: Lead with subtitles and make difficulty badges opt-in

The options page now has one card per feature, Subtitles first and Difficulty badges second, each with its enable switch followed by subsections. Previously difficulty filled four panels and subtitles one, so the page did not read as two features. Subtitles is the extension's main draw, and a separate difficulty extension already exists in the Chrome Web Store; this one should not compete with it by default. Reordering alone would still show badges on a fresh install, so `difficultyEnabled` now defaults to off, matching subtitles. The cost is that a fresh install does nothing visible until the options page is opened; opening it automatically on install is recorded in TODO.md. Users who never saved options run on the defaults, so changing a default would normally switch the feature off for them on update; that was acceptable here because the extension had no users besides its author.

## 2026-11-06: Save options automatically

Leaving the options page with unsaved changes silently discarded them. A leave-page warning (`beforeunload`) was considered, but Chrome shows only a fixed generic message and it treats the symptom. Saving every change immediately removes the unsaved state altogether, matches Chrome's own settings pages and most extension options pages, and fits the existing behavior of open Dreaming tabs updating live through storage change events. The cost is that a set of trial changes cannot be abandoned as a group; Restore defaults remains. Each write is one `chrome.storage.sync.set` per user action, far below sync's write-rate limits, and a failed write is reported on the page.

## 2026-11-06: Open the options page on first install

With every tool off by default, a fresh install looked like it did nothing. A background service worker now opens the options page on `onInstalled` with reason `install` only; opening it on updates or reloads would interrupt existing users for no reason. This adds the extension's first service worker but no permission. The same worker is the planned home for injecting the current content script into Dreaming tabs that were open during an install or update, which is kept as a separate change because it needs the `scripting` permission and a handover between old and new script copies.

## 2026-11-06: Refresh open Dreaming tabs with the scripting permission

After an install or update, Dreaming tabs that were already open kept the orphaned previous content script, which ignores settings changes while its key listeners and page observer keep running; users had to know to reload. The background worker now injects the manifest's own content-script files into open, non-discarded Dreaming tabs on `install` and `update`. This adds the `scripting` permission, which Chrome shows no install warning for; it is limited to packaged files (never code strings or functions), and a test now pins the manifest's permission list so future changes are deliberate. Reloading the tabs was rejected because it would interrupt a playing video. Two copies would otherwise run in the page, so each copy announces itself with a `dreaming-tools:replaced` DOM event, which reaches scripts from every extension context; a running copy that hears it switches all features off, synchronously, before the new copy starts. Verified in headless Edge on a live Dreaming page: after an extension reload the old copy cleared its classes, the new copy restored them, and a later settings change applied without a tab reload. An orphaned copy is not made to stop itself when it detects that it is orphaned, because if injection fails the stale copy with its last settings is better than none. YouTube embed frames are not refreshed, since each new video loads a new frame.

## 2026-11-06: Theme the options page with tokens and original preview art

The options page gained dark mode, so every color became a `:root` token with a dark-mode value, and a stylesheet test enforces that (every token redefined, no literal colors outside token blocks), so a later change cannot silently add a color that only works in one theme. Preview caption colors are fixed tokens because they imitate the players, which do not follow the page theme. Text moved to `rem` after the page was seen at a smaller-than-default browser font size, where fixed pixel sizes made headings and body text disagree. The blank preview blocks became a blurred, original kitchen illustration (`preview-scene.svg`) rather than a frame from Dreaming, to avoid copyright and branding concerns; the kitchen matches the sample subtitle line. Subtitles get one preview per player, because the Dreaming and YouTube players draw captions differently and a single preview misrepresented one of them; each uses the player's real container class so the shipped stylesheet is what is previewed. The reload note moved from the header to the bottom of the page once open tabs began refreshing themselves, since it is now a fallback rather than a required step.

## 2026-11-06: Leave Dreaming's subtitle transition alone

A reported font and size mismatch on Dreaming's player turned out to be Dreaming's own caption font, which differs from YouTube's; Dreaming shows it the same with no extension installed, and with de-emphasis revealed the measured styles and screen captures matched having it off exactly. The investigation did find that the extension's `transition` on `.shaka-text-container` replaced Dreaming's own `transition: bottom 0.1s`, so the subtitle line jumped instead of gliding when it moved. Moving the styles to the subtitle lines, as for YouTube, was tried and rejected: verified live, Shaka sets an inline `opacity: 1` on each line, which defeats the Hidden and Small and faint styles. Overriding it with `!important` would break the rule that the extension never overrides the player's own styles, and copying Dreaming's exact transition value would drift when Dreaming changes it. The extension now sets no transition on Dreaming's player, so its effects switch instantly there; YouTube's captions keep their 120 ms fade. The options-page Dreaming preview now mirrors the real line structure (a block line inside the container).


## 2026-11-07: Use Playwright for live-site browser tests

The live-site smoke tests were manual, and a first automation pass showed what an automated suite needs. It has to log in through a persistent browser profile, load the unpacked extension, drive the extension's own options page and service worker, send trusted keyboard input, and reach into the cross-origin YouTube frame. Claude in Chrome cannot open extension pages, and a hand-written CDP script worked but would have grown into a homemade test runner. Playwright (`@playwright/test`) covers all of these directly: persistent contexts, frames, trusted input, its own Chromium with extension loading, an installed-Edge channel, and traces and reports. That reverses the earlier view, for the fixture layer, that Playwright was too heavy: the cost is one dev dependency and a separate browser download. Nothing ships in the extension, and `npm ci` downloads no browser. The suite runs the packaged ZIP, not the working tree, so it tests what users install. It runs locally only, outside `npm test` and CI, because it depends on the live site and on a login. Logins happen by hand in a dedicated profile outside the repository, and no script handles credentials. A logged-out CI job is deferred until the tests prove stable against the live site.

## 2026-11-09: Live-suite rules for account state, extension reloads, and window blur

Three choices in the logged-in Playwright tests are not obvious from the code.

**Account state.** Driving Dreaming's player changes the account's subtitle language, which Dreaming stores server-side, so the logged-in project runs between a setup project that records the choice and a teardown project that restores it. A worker-scoped fixture was rejected because Playwright restarts its worker after a failed test, and the new worker would record the already-changed value as the original. The record is a file next to the test profile, and setup never overwrites one, so an interrupted run that never restored still remembers the true original. Tests never add to the Library or My list and never submit a comment; a page with nothing to check is skipped.

**Extension reloads.** The tab-refresh test runs in the installed Edge even when the rest of the suite runs in Playwright's Chromium. Chrome for Testing unloads an extension loaded from the command line when it calls `chrome.runtime.reload()`, and never loads it again, so that browser cannot model an update. Edge reloads it, as Chrome does for users. Calling the refresh code directly was rejected because it would skip the `onInstalled` path the test exists to cover.

**Window blur.** Headless browsers have no second window to switch to, so the window-blur tests dispatch the window's `blur` event. That exercises the same listener a real window switch triggers, but not the browser deciding to send it, which stays on the manual checklist.

## 2026-11-09: Series modal badges target both the old and new cover classes

Dreaming renamed the series modal's `.ds-series-modal__header` to `.ds-series-modal__hero`, which removed the cover's range badge. The extension now targets both classes in `SERIES_CARD_SELECTOR` and in the `position: relative` rule that anchors the badge. Replacing the old class was rejected: keeping it costs one selector and leaves the badge working if Dreaming rolls the change back or serves the two layouts side by side. Dreaming's own stylesheet already positions the hero, so the badge lands correctly without our CSS line today (checked by removing it and re-running the live test). The line stays as a safeguard against Dreaming dropping that positioning, and it matches the other card types.

## 2026-11-09: Drop the community beta label; publish ordinary releases

The publishing plan called for a recruited community beta before the store: Spanish and French testers, free and premium accounts, several desktop platforms. The beta was never announced to the Dreaming community, so no outside testers took part, and the beta label only marked GitHub releases as prereleases. Coverage now comes from the maintainer's manual passes and the live-site Playwright suite (Spanish and French, Chromium and Edge). Releases from 0.10.2 on are therefore ordinary GitHub releases, and `docs/BETA.md` became `docs/INSTALL.md`. The gaps a beta would have covered (Windows and Linux, premium accounts, display scaling, French by hand) are listed in each release's limitations rather than implied by a label. The `0.x` version still signals a young project, and the Chrome Web Store launch is a natural point for `1.0.0`. Separately, Dreaming Languages approved an earlier, difficulty-badges-only version of the extension in reply to the maintainer's outreach, so the contact item in phase 2 of `docs/PUBLISHING.md` is checked; its branding and support-channel questions stay open.

## 2026-11-11: Submit to the Chrome Web Store as is: current name, both tools

The store listing uses the published package unchanged: the name Dreaming Tools and both tools, each off by default. Two alternatives were considered and rejected: a distinct product name with "for Dreaming" as a description, and a subtitle-only store version. Both would need code changes and a new release for a risk the maintainer judged small, since Dreaming had approved the earlier, difficulty-badges-only version, a follow-up describing the subtitle tool and asking about the name got no specific answer either way, and other Dreaming-related extensions are listed in the store. The listing states that the project is unofficial and not affiliated with or endorsed by Dreaming Languages. If Dreaming objects, the extension will be withdrawn from the store.

## 2026-11-13: On the options page, the reveal key previews even from a focused select

The options page used the shared `isTypingTarget()` check, so a focused select took the reveal key instead of the preview. A select keeps focus after each change, so after choosing a subtitle style, pressing S reached the select's type-to-select, which picked "Small and faint" and saved it; on the Reveal select, whose options start with other letters, S seemed to do nothing (issue #26). The page now stands aside only in text fields: from a select the key previews and is prevented, so it never changes a setting. Arrow keys, Enter, and other letters still work in selects, and an open select list still receives keys directly; only type-to-select with the reveal key's letter is lost. Blurring each select after a change was rejected because it would move keyboard users' focus. The content script keeps the shared check, because on Dreaming's own pages a form control should keep its keys.

## 2026-11-13: Subtitle previews draw each player's controls; the YouTube preview is labelled for free accounts

The two subtitle previews looked alike apart from the caption box (issue #28). Each now draws its player's controls, static and as they look while showing, so the caption sits where it does on the site at the moment a viewer is most likely to look at it. The controls are original simplified icons in each player's colors; logos and YouTube's red play-button shape are left out, because the extension is unofficial. Animating the controls hiding was rejected: it adds motion without showing anything more about the subtitles. YouTube's large center pause button was left out because it would overlap the caption in a narrow window. The YouTube preview's label became "YouTube player (free accounts)", because Dreaming gives premium accounts its own player for every video (see SPEC.md, "Which player a video uses"), and a premium user would otherwise look for a player they never see.

## 2026-11-13: Release ZIPs are never silently replaced; test builds go to dist/dev/

The live suite and the store-screenshot script used to rebuild `dist/dreaming-tools-VERSION.zip`, so running them on a branch after a release replaced the released package with unreleased code of the same version number. It happened several times during the 1.1.0 work, once through a reviewer's `npm run package` in the shared working copy, and each time the released ZIP had to be restored from a copy. Now `npm run package` refuses to replace an existing ZIP whose contents differ (`--force` overrides), and the live suite and screenshots build and load a test copy in `dist/dev/`. The build is reproducible, so on a release commit the two are byte-identical, which keeps "the live suite tested this exact ZIP" checkable by comparing checksums. Rejected: tagging test builds with a different version (the extension would report a version that was never released) and packaging into a temporary directory per run (the test build could no longer be inspected after a failure).

## 2026-11-16: Prepare one manifest for Chrome and Firefox

Exploring a Firefox port, the manifest gained the two keys Firefox needs, leaving Chrome's behavior unchanged. Firefox does not run Manifest V3 background service workers, so `background.scripts` names the same `src/background.js` that `background.service_worker` names for Chrome; each browser reads its own key. `browser_specific_settings.gecko` holds the add-on ID that Firefox's store requires for MV3 extensions, and the data collection declaration (`none`) it requires for new submissions. The ID `dreaming-tools@jefelabs` is permanent once the add-on is listed, so it should be confirmed before the first Firefox submission. A separate Firefox manifest or build step was rejected: the extension's APIs (`storage`, `scripting`, `tabs`, `runtime`) all exist under Firefox's `chrome` namespace, so the only differences are manifest keys that each browser ignores in the other's. The packager now checks `background.scripts` against the runtime allowlist as it does `service_worker`. Firefox stays unsupported in SPEC.md until it is validated by hand: host access after a fresh install, promise-returning `chrome.*` calls, and the install-time tab refresh, since Firefox may already inject content scripts into open tabs. A first manual pass in Firefox on 2026-11-16, loaded with `web-ext run`, found site access granted for both hosts, the difficulty and subtitle tools applying settings, and the tab refresh working; `web-ext lint` reported no errors and one expected warning (Firefox ignores `background.service_worker`).

## 2026-11-16: Live tests close the first-install options tab in every profile

A live options test failed intermittently with "page.goto … interrupted by another navigation" (9 of 50 repeated runs on a reviewer's machine; not reproduced on the maintainer's Mac, even under CPU load). A probe showed the cause: `chrome.runtime.openOptionsPage()` reuses a blank tab instead of opening a new one, so when the first install finished just after a test opened its tab, Chrome navigated that tab mid-`goto`. The fixture already closed the first-install tab in the logged-in profile; it now does so in fresh profiles too, before every test, with a `firstInstallTab: "keep"` option for the one test that checks the page opens by itself. Fixing only `options.spec.js` was rejected because the badge specs open tabs the same way. The close helper also changed: it waited for a new-page event, but the options page can arrive by navigating the browser's initial blank tab, which fires none, so it timed out after 5 seconds without closing anything. It now polls every tab's URL, and closes the tab in under a second.

## 2026-11-16: Keep the subtitle tool in Dreaming Tools; no separate any-site extension

The 2026-11-11 idea of splitting subtitle de-emphasis into its own extension for any video site is dropped. It was reconsidered after learning that the community difficulty extension also has a Firefox version, which made a subtitle-only, cross-site extension look like the more distinctive product. Technically it was feasible: the feature works through two player types, Shaka (a library class, not a Dreaming one) and YouTube's caption markup, so youtube.com and other Shaka sites would mostly need site support and permissions, while plain HTML5 captions would need custom rendering because `::cue` cannot blur. But a paid, listen-first subtitle suite already covers that ground across the major streaming sites (Subtiltée, reviewed by the maintainer), and the maintainer judged the cross-site market not worth splitting the project. Dreaming Tools stays one extension with both tools, for Chrome and, once validated, Firefox. Its distinct value on Dreaming is the subtitle tool, which the community difficulty extension does not have.

## 2026-11-17: Support Firefox from 1.2.0, validated by hand; add a LICENSE file

Firefox becomes a supported browser in 1.2.0, published to Firefox Add-ons (AMO) with the same ZIP as the Chrome Web Store. The maintainer's manual passes in Firefox on macOS (2026-11-16 and 2026-11-17) covered site access after a fresh install, both players (Dreaming's player on a premium account, YouTube-served videos on a free account), the subtitle styles and reveal key, difficulty badges, and the install-time tab refresh; `web-ext lint` reported only the expected `background.service_worker` warning. The live Playwright suite stays Chromium and Edge only, because Playwright cannot load an extension into Firefox; Firefox is a manual row in the TESTING.md release matrix instead. Driving Firefox through Mozilla's own tooling (`web-ext` with Selenium or geckodriver) was rejected for now: it would duplicate the live suite for a browser whose differences so far are manifest keys, and the risky areas (rendering and the cross-frame reveal relay) were checked by hand. The add-on ID `dreaming-tools@jefelabs` is kept. The privacy policy now names Firefox Sync alongside Chrome Sync, since `chrome.storage.sync` syncs through the user's Mozilla account in Firefox. AMO asks for a license on listed add-ons, and `package.json` already declared MIT without a license file, so the repository gains the standard MIT `LICENSE`.

## 2026-11-17: CI fails on runtime advisories only; dev advisories are reported

A high-severity advisory against `picomatch` (GHSA-fc5q-39xc-vjpf) covered every published version, with no fix released, and reached the repository only through Vitest and Vite. CI's plain `npm audit` then failed on every pull request and on `main`, and branch protection blocked all merges, including the 1.2.0 release. The only automatic fix, `npm audit fix --force`, pins Vitest and its coverage plugin back to 3.1.4. The tests still pass on that version (checked by the reviewer), but the audit gets worse: `picomatch` stays, and older packages add 3 critical advisories (including `tinypool`), 4 high, and 4 moderate, 11 in all against 6. The extension package contains no npm packages, so dev tooling never reaches users. CI now fails on `npm audit --omit=dev` and runs the full `npm audit` as a non-blocking step so dev advisories stay visible in the CI log. `package.json` has no runtime `dependencies` today, so the blocking audit checks nothing yet and always passes; it starts guarding the extension only if a runtime dependency is added, which is the case it exists for. Rejected: waiting for an upstream fix (merges blocked for an unknown time), an admin merge override (leaves `main` red and repeats on the next PR), and an `--audit-level=critical` threshold (would also hide high-severity runtime advisories). The release checklist runs both audits; dev advisories are reviewed by hand before each release.

## 2026-11-19: Freeze the difficulty badges; new work goes to the subtitle tool

The community difficulty extension ("Dreaming Spanish Difficulty" on Firefox Add-ons, "Dreaming Spanish Numerical Series Difficulty" on the Chrome Web Store) is published for both Chrome and Firefox, so Dreaming Tools' difficulty badges are no longer the only way to see ratings on Dreaming in either browser. Removing the badges in a 2.0.0, or moving the subtitle tool to a new subtitle-only extension, was considered and rejected for now. The badge code is finished, tested, and off by default; removing it would mean a release, store reviews, and rewritten listings and privacy text for no gain to users; and a new extension would give up the existing store listings. The badges also do things the other extension does not: watch-page chips, a fill-missing mode, and a choice of style, size, and corner. They are frozen instead. Bugs and breakage caused by changes elsewhere in the extension are still fixed, but no new badge features are added. If a change on Dreaming's side breaks the badges in a way that needs real rework, they are removed in that release rather than rebuilt. New feature work goes to the subtitle tool, which the other extension does not offer.

## 2026-11-19: One store screenshot per subtitle style; a poster title on the series preview

The store screenshots showed only the blurred and revealed subtitles, so a visitor could not compare the styles. There are now four subtitle shots (hidden, blurred, small and faint, revealed) and the badge shot, which is the Chrome Web Store's limit of five. Each subtitle shot starts at "Subtitle appearance", because at 1280x800 a shot from the top of the page cut off the player previews, the one part that differs between styles. Firefox Add-ons shows a caption per screenshot, so the captions are kept in `STORE_LISTING.md`; Chrome shows none. A lighter kitchen scene for the subtitle previews was mocked up, because the black stove sits behind the subtitle line and hides most of the blur; the maintainer kept the current art. The series preview gained a poster title across the top, as on Dreaming's series covers, because without it the blurred coastline did not read as a series cover. The title is SVG text in a heavy system font (Impact where available), not outlined paths: the art is shown blurred, so a fallback font changes little.

## 2026-11-19: Jump back on reveal; auto-hide counts playback time

Learners react to a missed word a few hundred milliseconds to a couple of seconds late, so a reveal often showed the next line, not the one they missed. Two designs were considered. A rolling buffer of recent caption lines, shown on reveal, was rejected because it means reading subtitle text, which the privacy policy and store listings say the extension never does. Instead, a reveal can move the video back (`revealJumpBack`), so the player redraws the earlier line itself and the learner hears it again while reading. It defaults to Off, so nothing changes until a user chooses an amount. The values are fixed (1, 2, 3, 5, 10 seconds) rather than 0.1-second steps, because caption lines last seconds and finer steps cannot be told apart; both outside reviews (ChatGPT and Devin) suggested this. Hold mode stays: press and hold, read along as the line replays, and let go. Only a press that reveals jumps, and each later reveal jumps again, which is accepted as predictable instead of adding a separate "press again to go further back" option. A 500 ms guard stops keyboards that send auto-repeat as fresh presses from rewinding many times a second. The seek sets `currentTime` on the video element: a live probe on 2026-11-19 showed both players accept it cleanly, playing or paused, with their seek bars following, so neither player's own seek API is needed (YouTube's would need a main-world script and a message bridge). In YouTube-served videos the jump happens in the frame, which owns the video; the Dreaming page only forwards the key. The auto-hide clock moved from wall-clock time to playback time measured from the press, which Devin's review argued for and ChatGPT's argued against: on playback time, pausing to read keeps the text up, slower speeds stretch naturally, and the new When caught up choice is simply the press point itself. There are no users yet to be surprised by the change. If no video is found, numeric auto-hide falls back to a timer, and the options page preview, which has no video, keeps its timer and treats When caught up as Off. A Toggle key release used to re-apply the reveal, which, with the new watch on the video, dropped the playback auto-hide; releases, blurs, and timeouts now change the state only when it changes.

## 2026-11-20: Count key taps by release, and anchor auto-hide at the first tap

A unit-test matrix over every reveal setting and realistic key-tap sequences (`tests/subtitles-matrix.test.js`), written after Jeff found the feature did not behave as expected in exploratory use, showed three problems with the 2026-11-19 design. The 500 ms jump guard made the distance depend on tap speed: in Hold mode, three taps 150 ms apart moved back 3 seconds, three taps 750 ms apart moved back 9. A Toggle reveal whose jump was skipped (by the guard, or because a seek was in flight) had no When caught up point, so the subtitles stayed up until the next press. And each reveal set its own auto-hide point, so after a few taps back the text hid well before the point where the learner started.

The guard is gone. A keydown now counts as a new press only after the key's release or a window blur, which still stops keyboards that send auto-repeat as fresh presses (the reason for the guard) and lets every deliberate tap jump. Auto-hide is anchored at the first press of a series of reveals, which lasts while playback stays between the lowest jump and that press, so several taps back show the text until playback returns to where the learner started, and a reveal that could not jump still hides there. The range rule, rather than a time limit or a count of taps, was chosen because it needs no tuning and ends a series exactly when the learner leaves the replayed stretch: by catching up, or by seeking elsewhere. A 0.5 s slack below the lowest jump allows for players landing slightly short of a seek target. Known limit: if a release is lost without a window blur, the next press only completes the lost one and is ignored once.

## 2026-11-20: Fixes from Devin's review of jump back

Devin reviewed PR #44 at 53f07e2 and found five bugs, each with a failing test. A reveal pressed while a seek was still in flight did not jump, so tap speed still decided the distance when seeks were slow; the skip is gone, because `currentTime` reports a pending seek's target, so jumps add up. A When caught up reveal whose first jump was skipped (video not ready, an ad) never hid; it now hides where the jump would have landed back to. A series of reveals was only checked at the next press, so it carried over into a new episode loaded into the same element, or past a rewind with the player's own controls after catching up; the video is now watched while a series lasts, which ends it at once. The Cmd key's release now also stands in for a lost key release on macOS. Devin's test for that case modeled it as two keydowns with no keyup, which is exactly the keyboard auto-repeat this design treats as one press, so the test was rewritten to include Cmd.

Devin also predicted that a quick Hold tap ends before the player draws the earlier line. A live probe on 2026-11-20 (Hold, 3 s jump, both players, free test account) showed the opposite mechanism with the same result: both players draw the earlier line 7 to 30 ms after the press, but an 80 ms tap hides it again about 85 ms after the press, leaving it readable for about 60 ms. A 1.5 s hold showed it normally. Whether taps should show the text until playback catches up is a separate design decision, still open.

The flaky live Toggle test was not a buffering stall, as first thought. The live suite shares one persistent profile and `setSettings` merges into storage, so the test inherited another test's 2-second jump; its three presses then formed one series, and the text correctly hid 3 seconds past the first press, not the third. The suites' base settings now name every reveal setting, and the auto-hide checks follow the video's clock on both sides of the hide point.

## 2026-11-20: One reveal key with tap and hold, replacing Hold and Toggle

Hand-testing jump back, Jeff found that his fingers treated a few quick presses as one action ("go back this far") and the release as another ("now let me read"). Neither mode fit. In Hold, a quick tap rewound the video but hid the text again almost at once: a live probe showed both players draw the earlier line 7 to 30 ms after the press, while an 80 ms tap hides it about 85 ms after the press, leaving about 60 ms to read. In Toggle, a second tap hid the text instead of going further back, and the learner had to choose a mode up front. Devin's review proposed the fix that matches the gesture: holding shows the subtitles until release, and a tap (released within 300 ms, a fixed constant) does what the new After a tap setting says: Hide on release (default, today's Hold behavior, so new behavior stays opt-in), Show until caught up, or Show 3, 5, or 10 seconds past where the learner first pressed. Every press jumps back when Jump back is on, so tapping goes further back, and the hide point is the first press of the series. There are no users yet to retrain, which is why this was done before release rather than after.

Rejected: keeping Hold and Toggle with a third mode (more choices, and Toggle's second-tap-hides still fights the gesture); making the 300 ms threshold a setting (not a choice a learner can make sensibly, and slow fingers get hold behavior, the default, anyway); a press that only hides early (any press rewinds; a hold, which hides on release, is the way to hide early, and the text hides by itself once caught up). Toggle with auto-hide Off, which kept the text up until the next press, has no equivalent; it migrates to Show 10 seconds, the closest.

The spec was written and reviewed first (SPEC commits 1a0b96e and 2ca9dc7). Devin's review of it found that a hide point set at the press could hide the text while the key was still held, so a hide point applies only after a tap's release; that hold time must come from the events' own timestamps and travel with the release forwarded to the YouTube frame, rather than be guessed from message arrival times; that the stand-in release from Cmd needs the same, and a release with no press pending must do nothing; and that a click on the YouTube video, which moves focus into its frame, must not forward a blur that hides the text. Migration maps 1.2.0's settings only when After a tap is not yet stored, because a second device still on 1.2.0 can write the old keys back through sync storage, and the background worker writes the new key before removing the old ones. Chrome's service worker loads settings.js with importScripts for this; Firefox lists it among the background scripts.
